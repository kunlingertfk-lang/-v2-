# 颜色识别提示词规范

本文档用于规范后续基于颜色识别功能继续开发时的提示词写法。目标是让提示词清晰、有边界、有验证要求，并**与当前真实代码结构对齐**，避免提示词描述的分层与实际代码脱节，导致新代码放错位置。

> 使用前提：写提示词前，先阅读第 2 节「真实代码结构与分层契约」和第 3 节「字段注册表」，这是与代码对齐的事实基础。规范描述的分层若与代码不符，以代码为准并在本规范中修订。

## 1. 写提示词的基本原则

一条好的开发提示词应包含六类信息：

```text
背景上下文
  -> 当前功能已经实现到什么程度（引用第 2 节真实结构，不要凭印象）

目标
  -> 这次明确要新增、修复或整理什么

范围
  -> 哪些文件/模块允许改，哪些不允许改

约束
  -> 技术路线、兼容要求、分层归属、禁止事项

验收
  -> 怎么证明做完了

输出
  -> 需要代码、文档、计划、测试还是只要分析
```

不建议只写：

```text
帮我优化颜色识别。
```

建议写成：

```text
基于当前颜色识别实现（见 docs/FID/ColorRecognition/颜色识别提示词规范.md 第 2 节），
在不改变现有模板 JSON 兼容字段的前提下，新增 XXX。
先判断本次属于 UI 面（2A）还是 API 面（2B），按对应落点改：
UI 控件改 ColorRecognitionDialog + ui/ColorRecognitionDialog.ui，
配置字段按第 3 节字段注册表登记并在 Adapter 解析，
算法核心改 ColorRecognitionHalconRunner，必须用 HALCON 算子。
完成后运行 smoke、qmake、make，并说明修改文件和验证结果。
```

## 2. 真实代码结构与分层契约

> V2 算法整理的目标合同见 `颜色识别算法V2整理设计.md`。当前已落地 HSV 直方图与 CIELAB GMM 双后端，通过 `recognitionBackend` 显式选择；两套模型和 score 语义隔离且不自动 fallback。

> 这是当前代码的真实职责分布，不是理想设计。颜色识别的职责**按 UI 面与 API 面划分**：UI 面管交互与视觉，API 面管数据与算法契约。后续开发先判断任务属于哪一面，只读对应面的落点清单，避免在 2000 行 Dialog 里盲目定位。若需调整分层（如把配置序列化从 Dialog 抽到 Adapter），应作为独立重构任务单独立项，不在功能开发提示词中顺带做。

### 2.3 API 面落点清单

API 面管数据与算法契约。改配置字段、算法、payload 时按下表落点。

| 逻辑类型 | 落点文件 | 关键方法（行号级） |
|---|---|---|
| **配置写入（ToolConfig 序列化）** | `ColorRecognitionDialog` | `toToolConfig()`(476) / `toolConfig()`(547) / `configuration()`(465) |
| **配置回显** | `ColorRecognitionDialog` | `loadFromConfig()`(557) |
| **配置读取（ToolConfig → Runner Config）** | `ColorRecognitionAdapter::run()` | 用 `intParam`/`boolParam`/`stringParam`/`rectFromJson` 工具函数解析 |
| 算法核心（特征提取、判别） | `ColorRecognitionHalconRunner` | 必须 HALCON 算子；缺符号返回错误，不 fallback |
| payload / overlay 输出 | `ColorRecognitionHalconRunner` | 字段名按第 3 节注册表，UI 侧只读不造 |
| HALCON runtime / license / so 路径 | `HalconRuntimePaths` | 不在 Runner 里硬编码路径 |

**配置抽象铆点**：`ColorRecognitionDialogConfig configuration()`(465) 返回结构体（定义在 `ColorRecognitionDialog.h:34`），是 UI 状态到 ToolConfig 的中间抽象。新增配置字段时，可先扩 `ColorRecognitionDialogConfig` 结构体，再由 `toToolConfig()` 序列化、`loadFromConfig()` 回显、`Adapter::run()` 解析，三处对齐。

### 2.4 关键提醒：配置读写分离（API 面核心）

当前配置层职责是**分裂**的，这是最容易放错位置的地方：

- **写配置**（UI 状态 → `ToolConfig.params` JSON）：在 `ColorRecognitionDialog::toToolConfig()`（约 476 行起）。
- **读配置**（`ToolConfig.params` JSON → `ColorRecognitionHalconConfig` 结构体）：在 `ColorRecognitionAdapter::run()`（用 `intParam`/`boolParam`/`stringParam`/`rectFromJson` 等工具函数）。

**新增字段必须两头都改**：Dialog 的 `toToolConfig()` 写入 + `loadFromConfig()` 回显，Adapter 的 `run()` 解析。只改一头会导致保存了读不出，或读出了没保存。规范第 5 节模板已强制要求两边都列。

### 2.5 已实现功能（固定上下文）

```text
当前颜色识别已实现：
- 主界面 ColorRecognitionDialog（UI + ROI 交互 + 测试调度 + 配置序列化 + 模板管理，单文件约 2000 行）。
- 模板创建/编辑对话框 ColorTemplateDialog。
- 配置保存/回显在 Dialog 的 toToolConfig() / loadFromConfig()；Adapter 只做 ToolConfig → ColorRecognitionHalconConfig 解析。
- ColorRecognitionHalconRunner 负责 HALCON 直方图特征提取和识别。
- 支持矩形检测 ROI、圆形检测 ROI、屏蔽多边形。
- 测试运行和工具页/主览窗口结果展示必须显示检测 ROI 框；不得隐藏 runner 输出的 `ROI` 结果 overlay。
- 当前 HSV 后端支持类别相似度（旧配置枚举 `dominant_ratio`）和整体相似度 `histogram_intersection`；新模板的类别相似度为每类最多 Top-3 样本交集相似度均值，结果不再伪称像素“主颜色占比”。
- HSV 分类器与特征签名分离：新模板使用 `hsv_category_topn_intersection_v1`，旧模板缺字段时保持 `hsv_category_best_sample_v2`；分类器 hash 不匹配必须拒绝运行。
- 支持 brightnessEnabled=false 的 H/S 二维联合直方图，以及 brightnessEnabled=true 的 H/S/V 线性直方图。
- 特征使用严格 `featureSignature`；禁止 H/S 与 H/S/V 按长度对齐，参数变化后模型进入 `stale` 并要求重新采样。
- 位置修正保留 `enable/source/sourceId` 干净接口；未实现时开启即返回 `unsupported_position_correction`，不静默继续识别。
- `knnK`、`knnDistance` 已从 Runner、Adapter 与新保存配置删除；高级参数区只保留未来 UI 扩展位置。
- 8/16 位彩色输入通过 HALCON 处理；16 位必须提供 `validBits/bitShift`，Mono 输入明确返回不支持。
- HALCON runtime 在颜色识别内部按符号 profile 缓存；生产链无 OpenCV Bhattacharyya 调试路径。
- GMM B1 核心建模已实现：HALCON CIELAB a/b 或 L/a/b、等量确定性采样、GMM 训练、严格 hash/Base64/反序列化产物验证。
- GMM B2/B3 已实现：UI 后端选择、8/16 位无损 ROI、模型建立/保存/回显/校验和独立 stale 管理，以及 Adapter 生产分类、rejection、类别面积、置信度/覆盖率判定和结果展示；任一 GMM 错误均禁止回退 HSV。
- 色谱特征和 HALCON 颜色分割/聚类只保留接口，暂未实现。
```

## 3. 字段注册表（单一事实源）

> 新增字段后必须更新此表。UI、Adapter、Runner 三处用到的字段名必须与此表一致，避免拼写漂移。「所属面」标注该字段在哪一面被读写，帮助判断改动落点。
>
> 本表只记录当前已落地代码的字段合同。V2 目标字段、模型状态和 payload 在实施前以 `颜色识别算法V2整理设计.md` 第 5 节为准；每个实施阶段落地后，必须同步回写本表，不得将尚未实现的 V2 字段误报为当前能力。

## 4. 开改前必须确认的易错点（pre-check）

发提示词或动手前，先逐条确认以下 AI 实际最常犯的错。任何一条不满足都先补齐再继续：

```text
[ ] UI 改动：是否同时检查 ui/ColorRecognitionDialog.ui 与 ColorRecognitionDialog.cpp？
    新增控件必须 .ui 加控件 + Dialog 代码接行为，双写。
[ ] 配置新字段：是否两头都改？
    Dialog::toToolConfig() 写入 + loadFromConfig() 回显 + Adapter::run() 解析，三处对齐。
[ ] payload 字段名：是否与第 3 节注册表完全一致？
    UI 侧只读 payload，不得造新字段名；Runner 输出字段名不得拼写漂移。
[ ] HALCON 算子链：是否已列出并用 HALCON 算子？
    缺符号返回明确错误，不允许 fallback 到 OpenCV/自写算法/第三方库。
[ ] 位置修正占位：开启未实现能力时是否返回 unsupported_position_correction？
    不得静默忽略，不得假报已应用；错误 payload 仍保持 positionCorrectionApplied=false。
[ ] 任务归属面：本次是 UI 面（2A）还是 API 面（2B）还是跨面？
    只读对应面落点清单，避免在 2000 行 Dialog 里盲目搜索。
```

## 5. 必须写清楚的约束

### 5.1 算法约束

```text
算法核心必须使用 HALCON 已有算子、类或过程。
实现前必须先确认所需 HALCON 算子可用，并列出算子链。
不允许使用 OpenCV、自写算法或第三方库替代核心算法。
OpenCV 只允许作为图像容器、采集、显示或格式桥接。
HALCON runtime、license 或符号缺失时必须返回明确错误，不允许 fallback。
```

### 5.2 分层约束

```text
先判断任务属于 UI 面（2A）还是 API 面（2B），按对应落点清单改动，不得跨层：
- UI 与交互逻辑放 ColorRecognitionDialog + ui/ColorRecognitionDialog.ui，不得下沉到 Adapter 或 Runner。
- 配置写入只在 Dialog::toToolConfig() / loadFromConfig()，配置读取只在 Adapter::run()。
  新增字段必须两头都改，并在第 3 节字段注册表登记。
- 算法核心只在 ColorRecognitionHalconRunner，Adapter 不写算法，Dialog 不调 HALCON。
- payload / overlay 字段名以第 3 节注册表为准，UI 侧只读不造新名。
- HALCON runtime / so 路径走 HalconRuntimePaths，不在 Runner 硬编码。
功能开发中不顺带做跨文件重构；如需调整分层，单独立项。
```

### 5.3 UI 约束

```text
UI 必须遵守当前颜色识别界面布局：
- 左侧白底黑字参数区。
- 右侧图像预览区。
- 基础 / 全部 分段切换。
- 配置项按卡片分区。
- 控件颜色保持白底黑字。
- 检测 ROI、模板样本 ROI、屏蔽区域的交互状态不能互相污染。
```

### 5.4 兼容约束

